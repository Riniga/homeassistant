# Development Setup

## Overview

Two working copies of this repository exist:

* **Desktop** (VS Code) — where most editing happens.
* **Home Assistant** (Raspberry Pi, `/homeassistant`) — where the configuration actually runs.

They sync through GitHub using the direct-to-`main` workflow described in `docs/standards/git.md` — no feature branches or pull requests, just commit and push.

## One-Time Setup

### Desktop

* Clone the repository.
* Set up the Python environment (see below) for `scripts/export_inventory.py` and tests.

### Home Assistant (Raspberry Pi)

Terminal access is via a real SSH client (PuTTY), not the add-on's in-browser terminal — the web terminal proved unreliable, so direct SSH was configured instead.

1. Install the **Terminal & SSH** add-on if not already installed: Settings → Add-ons → Terminal & SSH.
2. In the add-on's configuration, note the SSH port (`22222`) and the `root` login password it's configured with.
3. Connect with PuTTY: host = the Home Assistant Pi, port `22222`, login as `root` with the password from step 2. Never write that password into this repository or any documentation — see `docs/standards/git.md`.
4. Over that SSH session, generate an SSH key: `ssh-keygen -t ed25519`
5. Add the public key to GitHub: GitHub → Profile → Settings → SSH and GPG keys → New SSH key.
6. Test the connection: `ssh -T git@github.com`
7. Go to the config directory: `cd /homeassistant`
8. Point the local repo at the SSH remote: `git remote set-url origin git@github.com:Riniga/homeassistant.git`
9. Verify: `git remote -v`

Day-to-day terminal access (for the sync steps below) is the same: open PuTTY, connect to port `22222`, log in as `root`.

### Python Environment (desktop)

`environment.yml` defines a conda environment (`ha`, Python 3.13, `pytest`) used for `scripts/export_inventory.py` and its tests.

```bash
conda env create -f environment.yml
conda activate ha
```

## Day-to-Day Sync

### Home Assistant → GitHub

When automations, scenes, or scripts are changed through the HA UI:

```bash
git status -s
git add . && git commit -m "message" && git push origin main
```

### GitHub → Home Assistant

When changes are made on the desktop and pushed:

```bash
git pull origin main
ha core check
```

Restart only if the change requires it, and only after a successful check:

```bash
ha core restart
```

## Safe Rollout for Live, Non-Regenerable Files

Most files this repository stops tracking (cache, lock, and log files) are safely regenerated by Home Assistant and need no special handling — a normal `git pull` deletes them from disk on the Pi and HA recreates them as needed.

Some files are different. `zigbee.db` (Zigbee network/device-pairing state) is live data with no automatic regeneration. If a commit stops tracking a file like this, `git rm --cached` on the desktop only removes it from the index and leaves the working copy in place — but the same commit applied via `git pull` on another machine becomes an actual working-tree deletion there.

Before pulling a commit that untracks a live, non-regenerable file:

1. Take a full Home Assistant backup: Settings → System → Backups → Create backup.
2. Copy the file into the already-gitignored `backups/` folder as an extra local safety net:
   ```bash
   mkdir -p backups
   cp <file> backups/<file>.bak
   ```
3. Pull. The tracked copy will be deleted from disk — this is expected.
4. Restore it from the backup copy:
   ```bash
   cp backups/<file>.bak <file>
   ```
   It stays in place from then on, since it now matches `.gitignore` and no future pull touches it.

This happened for real with `zigbee.db` during the initial repository cleanup (`docs/plans/001-project-foundation.plan.md`, Phase 1) — recovered via `git reflog` → `git reset --hard <pre-pull commit>` on the Pi, then re-synced using the steps above.
